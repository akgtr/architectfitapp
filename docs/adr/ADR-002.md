# ADR-002: Использование API Gateway и BFF для мобильного клиента

---

## Context

Система включает несколько доменных сервисов (Training, Community, Challenges, Plans, Commerce, Integrations, Identity), каждый со своими API и моделями данных. Мобильное приложение должно:

- решать комплексные сценарии (экран «Дом», «Лента», «Прогресс», «План», «Инвентарь») одним‑двумя запросами;  
- минимизировать сетевые обращения и объём передаваемых данных;  
- работать в условиях нестабильной сети.

При этом важно:

- централизованно решать задачи аутентификации/авторизации, rate limiting, логирования и мониторинга;  
- скрыть внутреннюю структуру микросервисов от мобильного клиента, чтобы можно было эволюционировать backend без обязательных апдейтов приложения.

---

## Decision

Принято решение:

- Использовать **API Gateway** как единую точку входа для мобильного приложения.  
- Реализовать **Backend for Frontend (BFF)**‑слой для мобильного клиента:  
  - BFF агрегирует данные из нескольких доменных сервисов и возвращает клиенту оптимизированные DTO, соответствующие конкретным экранам и сценариям.  
  - BFF отвечает за оркестрацию запросов к Community, Training, Plans, Challenges, Commerce, Integrations.

Высокоуровневая схема:

- Mobile App → API Gateway/BFF → доменные сервисы.

---

## Status

- **Accepted** для первого релиза и ближайших этапов развития.  
- Может быть расширен отдельными BFF‑ами (например, для админского веб‑интерфейса или B2B‑портала) по мере необходимости.

---

## Consequences

### Положительные

- **Сокрытие внутренней архитектуры:**  
  - Клиент знает только публичные endpoint’ы BFF, а не конкретные сервисы и их контракты.  

- **Оптимизация под UX мобильного клиента:**  
  - Для сложных экранов (например, «Дом» с лентой, планом, прогрессом и промо) BFF может сделать несколько внутренних вызовов и вернуть агрегированный ответ.  
  - Снижение количества сетевых запросов и экономия батареи/трафика.

- **Централизованная безопасность и кросс‑функциональные политики:**  
  - Единое место применения аутентификации/авторизации, rate limiting, базовых security‑фильтров.  

- **Упрощение эволюции backend:**  
  - Можно менять структуру доменных сервисов и внутренние API, сохраняя стабильный контракт BFF для мобильного клиента.

### Отрицательные

- **Дополнительный слой сложности:**  
  - BFF сам является сервисом, который нужно разрабатывать, тестировать и сопровождать.  

- **Риск «раздувания» BFF:**  
  - При неправильной дисциплине BFF может начать содержать бизнес‑логику, которая должна находиться в доменных сервисах.  

- **Точка потенциального узкого места:**  
  - При неверной реализации BFF/API Gateway могут стать bottleneck по производительности и доступности.

---

## Alternatives considered

1. **Прямые вызовы доменных сервисов из мобильного приложения**  
   - Плюсы:  
     - без дополнительного слоя;  
     - каждая команда может разрабатывать свой API независимо.  
   - Минусы:  
     - клиент «знает» внутреннюю архитектуру, что усложняет её эволюцию;  
     - больше запросов с клиента (нужно опрашивать несколько сервисов на один экран);  
     - сложнее централизовать безопасность, логирование и throttling.  
   - Отклонено: не соответствует требованиям по UX, управляемости и эволюции.

2. **Только API Gateway без BFF (тонкий шлюз)**  
   - Плюсы:  
     - проще реализовать;  
     - основная логика остаётся в доменных сервисах.  
   - Минусы:  
     - мало возможностей для агрегации и адаптации ответов под специфические мобильные сценарии;  
     - сложная логика сборки экранов перекладывается на клиент.  
   - Отклонено: увеличивает сложность клиента и количество сетевых вызовов.
