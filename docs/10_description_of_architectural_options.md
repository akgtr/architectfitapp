## 10. Анализ и описание архитектурных опций и обоснование выбора

### 10.1. Общий стиль архитектуры: монолит vs модульный монолит vs микросервисы

**Опции:**

1. **Классический монолит**
    - Плюсы: простота разработки и деплоя, меньше инфраструктурной сложности.
    - Минусы: сложность масштабирования отдельных доменов (community, тренировок, уведомлений), высокий риск взаимного влияния модулей, трудности с независимым развитием команд.
2. **Модульный монолит**
    - Плюсы: лучшее разделение доменов в коде, относительно простой деплой, возможность постепенной миграции к микросервисам.
    - Минусы: масштабирование всё ещё, по сути, единой кодовой базы; ограничения по технологиям; риски «скрытых» зависимостей.
3. **Микросервисная архитектура с доменным разбиением**
    - Плюсы: независимое масштабирование доменов (Training, Community, Commerce, Integrations), лучшая изоляция отказов, возможность отдельных технологических решений (например, отдельная БД для аналитики).
    - Минусы: выше сложность (DevOps, observability, управление данными, консистентностью), требования к зрелости команды.

**Выбор:**

- Для проекта выбрана **микросервисная / многосервисная архитектура с доменным разбиением**, поскольку:
    - критичны масштабируемость и отказоустойчивость;
    - домены достаточно чётко отделимы (тренировки, соц. функционал, commerce, интеграции, security);
    - компания уже активно использует облака и имеет штат разработчиков, готовых к работе с несколькими технологиями.


### 10.2. Синхронное vs асинхронное взаимодействие между сервисами

**Опции:**

1. **Только синхронные REST‑вызовы**
    - Плюсы: простая модель, легче отладка, привычный стек.
    - Минусы: сильная связанность, каскадные таймауты, слабая устойчивость к пикам (массовые челленджи, рассылка уведомлений).
2. **Гибрид: REST для команд и чтения + Event‑driven для событий**
    - Плюсы:
        - запросы/ответы для UX‑критичных операций;
        - события для ленты, уведомлений, аналитики и commerce;
        - возможность независимого наращивания потребителей событий.
    - Минусы: дополнительная сложность в управлении событиями и eventual consistency.
3. **Чисто событийный подход (event sourcing + CQRS)**
    - Плюсы: максимальная гибкость для аналитики и реактирования на события, высокое расцепление.
    - Минусы: высокая сложность реализации и обучения, не всегда оправдана в MVP.

**Выбор:**

- Применяется **гибридный подход**:
    - **REST/JSON** через API Gateway/BFF для клиентских сценариев (создание/просмотр тренировок, управление планами, участие в челленджах).
    - **Шина событий (Event Bus)** для транслирования фактов: завершение тренировок, обновление прогресса в челленджах, статус инвентаря, триггеры для уведомлений и аналитики.
- Это даёт баланс между управляемой сложностью и нужной масштабируемостью.


### 10.3. API‑слой: прямые вызовы сервисов vs API Gateway vs BFF

**Опции:**

1. **Прямые вызовы сервисов с клиента**
    - Плюсы: отсутствие дополнительного слоя.
    - Минусы: сложность управления безопасностью, версионированием и маршрутизацией; необходимость клиенту знать структуру backend.
2. **Единый API Gateway**
    - Плюсы: централизованный вход, безопасность, rate limiting, базовый роутинг.
    - Минусы: сложнее реализовать специфическую агрегацию ответов под разные клиенты.
3. **Комбинация API Gateway + BFF для мобильного клиента**
    - Плюсы: возможность собирать ответы из нескольких сервисов и выдавать клиенту оптимизированные DTO, скрывая внутреннюю структуру.
    - Минусы: дополнительный слой логики, который надо сопровождать.

**Выбор:**

- Используется **API Gateway + BFF**:
    - API Gateway отвечает за аутентификацию, авторизацию, технические кросс‑функциональные задачи (throttling и т.п.).
    - BFF (может быть реализован как часть gateway или отдельный сервис) агрегирует данные от Community, Training, Plans, Commerce и выдаёт клиенту удобные «экраны» (home, лента, прогресс, план).
- Это уменьшает «болтовню» по сети и упрощает эволюцию API для мобильных приложений.


### 10.4. Модель данных и хранилища: единая БД vs per‑service DB + DWH

**Опции:**

1. **Единая общая БД для всех сервисов**
    - Плюсы: простая схема, единый источник истины, простые JOIN‑ы.
    - Минусы: сильная связанность сервисов, сложность масштабирования, риск «узкого горлышка» и конфликтов команд.
2. **Отдельные БД на сервис/домен + интеграция через события**
    - Плюсы: независимость доменов, оптимизация типа хранилища под нагрузку, лучшая изоляция.
    - Минусы: сложнее обеспечивать консистентность, возможна дубликация данных.
3. **Гибрид: общий operational DB на стартовом этапе + выделенные хранилища для тяжёлых доменов и отдельный DWH**
    - Плюсы:
        - компромисс между сложностью и независимостью;
        - проще запускать MVP;
        - можно постепенно выносить домены в отдельные БД.
    - Минусы: необходимо следить за постепенным ростом сложности и переездом доменов.

**Выбор:**

- На **MVP‑этапе** использовать **единый operational DB** (например, PostgreSQL) с чётким логическим разделением схем по доменам (Training, Community, Commerce, Security).
- Для аналитики и отчётности — **отдельный DWH/Data Lake** с загрузкой данных через события/ETL.
- В дальнейшем допускается вынос наиболее нагруженных доменов (например, Feed/Challenges, Analytics) в отдельные хранилища.

### 10.6. Наблюдаемость: встроенная vs внешняя

**Опции:**

1. **Минимальная observability (логи только по ошибкам)**
    - Плюсы: дешево по времени старта.
    - Минусы: плохо управляемая распределённая система, сложность диагностики.
2. **Полноценный стек observability (логи, метрики, traces)**
    - Плюсы: управляемость, возможность операционных и продуктовых выводов.
    - Минусы: дополнительные ресурсы и сложность настройки.

**Выбор:**

- Сразу проектируется **полноценная наблюдаемость**:
    - централизованные логи;
    - метрики по сервисам и бизнес‑операциям;
    - распределённая трассировка.
- Это обосновано критичностью сценариев (тренировки, челленджи, интеграции с устройствами) и необходимостью контролировать SLA.


### 10.7. Безопасность: «встроенная» (security by design) vs «поверх»

**Опции:**

1. **Добавление безопасности поверх готовой функциональности**
    - Плюсы: быстрый старт.
    - Минусы: риски пропуска критичных путей, технический долг, дорогое исправление.
2. **Security \& Privacy by design**
    - Плюсы: корректная модель угроз, минимизация хранения чувствительных данных, встроенная поддержка приватности.
    - Минусы: выше начальные затраты, необходимость участия специалистов по безопасности с ранних этапов.

**Выбор:**

- Принцип **security \& privacy by design**:
    - отдельный домен Identity \& Security;
    - явная модель данных и уровней доступа;
    - проектирование API и событий с учётом минимизации экспонируемых данных.


### 10.8. Вывод

- Для проекта выбран **микросервисный, event‑driven подход** с API Gateway/BFF, общим operational DB на старте и отдельным аналитическим хранилищем.
- Взаимодействие между сервисами реализуется через комбинацию синхронного REST для UX‑критичных операций и асинхронных событий для ленты, уведомлений, аналитики и commerce.
- Структуры данных и API проектируются доменно и описываются отдельно, с версионированием и ориентацией на независимую эволюцию доменов.
- Наблюдаемость и безопасность рассматриваются как базовые архитектурные требования, а не «последующие доработки», что согласуется с выбранными атрибутами качества.
