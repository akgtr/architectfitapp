## 14.5 Безопасность

Этот подпункт описывает, как в архитектуру встроены меры безопасности и приватности с учётом OWASP API Security и особенностей фитнес‑приложения с чувствительными данными здоровья и геолокации.

### 14.5.1 Аутентификация и авторизация

- **Аутентификация**
    - Внешний Brand SSO (OIDC/SAML) как единый источник идентичности, серверы не хранят пароли.
    - Mobile App использует OAuth2/OIDC‑токены доступа/обновления, хранение токенов в защищённом хранилище на устройстве.
- **Авторизация (OWASP API1/5/3)**
    - Object‑level authorization: каждый запрос к тренировке, профилю, ленте проверяется по `userId` и ролям, чтобы избежать Broken Object Level Authorization.
    - Property‑level authorization: сервисы не возвращают поля, на которые нет прав, что снижает риск Excessive Data Exposure / Broken Object Property Level Authorization.
    - Function‑level authorization: административные функции (модерация, служебная аналитика) отделены и защищены отдельными ролями.


### 14.5.2 Защита данных и приватность

- **Шифрование данных**
    - Шифрование **в транзите**: везде HTTPS/TLS, mTLS внутри кластера для взаимодействия микросервисов (Zero Trust, «никому не доверять по умолчанию»).
    - Шифрование **на диске**: включено для всех управляемых БД и объектного хранилища (AES‑256, KMS/Key Vault).
- **Изоляция чувствительных данных**
    - Геоданные и сырые health‑метрики хранятся отдельно от идентификационных данных, с минимальным набором связей.
    - Для аналитики используются анонимизированные/псевдонимизированные наборы (усечение маршрутов, замена идентификаторов).
- **Privacy by Design / by Default**
    - Консервативные настройки приватности по умолчанию (минимальная видимость профиля и тренировок).
    - Гранулярные настройки приватности для профиля, тренировок, маршрутов, лидербордов и sharing‑сценариев.
    - Простые механизмы удаления/экспорта данных (право быть забытым, прозрачность обработки).


### 14.5.3 Защита API и инфраструктуры

- **OWASP API Security Top 10 меры**
    - Валидация входных данных и строгие схемы DTO (JSON Schema/OpenAPI) для сокращения поверхности атак.
    - Rate limiting и защита от Unrestricted Resource Consumption (API4:2023) на уровне API Gateway/BFF для тяжёлых операций.
    - Жёсткий контроль конфигураций и секретов (Security Misconfiguration, API8:2023): секрет‑менеджер, отсутствие секретов в коде, закрытые debug‑эндпоинты.
    - Инвентаризация API‑версий и хостов (API9:2023) в документации и системе мониторинга, своевременное выключение устаревших версий.
- **Zero Trust внутри кластера**
    - mTLS между сервисами, валидация workload‑identity (service accounts, SPIFFE/SPIRE или mesh‑идентичность).
    - Политики сетевой сегментации (NetworkPolicy) ограничивают, какие Pod’ы могут говорить друг с другом и с БД.


### 14.5.4 Управление третьими сторонами и интеграциями

- Ограничение и каталогизация всех внешних интеграций (аналитика, пуш‑провайдеры, wearables), минимизация передаваемых данных.
- Проверка провайдеров на наличие сертификаций (ISO 27001, SOC 2) и заключение Data Processing Agreements.
- Регулярный пересмотр зависимостей и обновление SDK/библиотек безопасности.


### 14.5.5 Мониторинг, аудит и реагирование

- Централизованный сбор и корреляция логов безопасности, включая события авторизации, доступ к чувствительным данным и изменения приватности.
- Настроенные алерты для аномалий (резкий рост ошибок аутентификации, подозрительные паттерны запросов к API, массовые экспорты данных).
- Регулярные security‑аудиты, пентесты и проверка API на типовые OWASP‑уязвимости.

### 14.5.6 Таблица «угроза → контроль» для geo/health‑данных

| Категория (LINDDUN/STRIDE) | Угроза для geo/health‑данных | Контроль/мера в архитектуре |
| :-- | :-- | :-- |

| Identifying | Комбинация геолокации, времени и редких health‑паттернов (болезнь, реабилитация) позволяет однозначно идентифицировать человека.  | Отдельное хранение идентификаторов и сырых geo/health‑метрик, жёсткий контроль доступа, показ только агрегатов в публичных интерфейсах.  |
| Non‑repudiation | Логи тренировок и health‑данных могут использоваться как доказательство присутствия/деятельности в конкретном месте и времени.  | Ограничение сроков хранения сырых логов, анонимизация в аналитике, прозрачная политика хранения и возможность удаления данных пользователем.  |
| Detecting | Наблюдая за онлайновым статусом, частотой тренировок и локацией, злоумышленник может отслеживать присутствие/отсутствие дома. | Грубое квантование времени/локации в публичных данных, отсутствие «онлайн‑статуса», строгие настройки приватности по умолчанию.  |
| Data Disclosure | Утечка БД с маршрутами и health‑метриками или неправильная конфигурация API может раскрыть чувствительные данные.  | Шифрование в транзите и на диске, сегментация БД, минимизация данных в ответах API, тесты против OWASP API Top 10, регулярные security‑аудиты. |
| Unawareness | Пользователь не понимает, что именно и кому показывается (маршруты, пульс, время тренировок), и какие риски это создаёт. | Ясные UI‑подсказки, онбординг по приватности, «центр приватности» в приложении, явные опции opt‑in/opt‑out для sharing/лидербордов.  |
| Non‑compliance | Нарушение требований по обработке health‑данных и геолокации (согласия, цели обработки, сроки хранения).  | Централизованный сервис Identity \& Privacy с хранением согласий и политик, аудит операций, механизмы экспорта/удаления данных, DPIA.  |
| STRIDE – Spoofing | Злоумышленник выдаёт себя за пользователя и получает доступ к истории geo/health‑данных.  | OIDC/OAuth2 с MFA (по возможности), защищённое хранение токенов, mTLS внутри кластера, строгая проверка токенов в BFF и сервисах.  |
| STRIDE – Tampering | Модификация маршрутов или health‑метрик (подмена результатов челленджа, искажение медицинской картины). | Контроль целостности на сервере, write‑only поток от клиента к backend, запрет редактирования сырых данных, цифровые подписи/хэши при необходимости.  |
| STRIDE – Information Disclosure | Перехват трафика или доступ к незашифрованным логам с geo/health‑данными.  | TLS везде, строгие политики логирования (без сырых geo/health в логах), маскирование данных в мониторинге и алертах.  |
| STRIDE – Denial of Service | Атака на API или БД, из‑за которой пользователь теряет доступ к своим health/geo‑данным в критичный момент.  | Rate limiting, WAF перед API Gateway, авто‑масштабирование, отдельные лимиты и ресурсные квоты для тяжёлых запросов (лента, экспорт). |
