## 9. Анализ и список нефункциональных требований

### 9.1. Масштабируемость

1. **Горизонтальное масштабирование сервисов**
    - Система должна поддерживать горизонтальное масштабирование ключевых сервисов (Training, Community, Feed, Challenges, Notifications, Integrations) без изменений в клиентских приложениях.
    - Все статeless‑компоненты должны корректно работать в нескольких инстансах за балансировщиком.
2. **Рост нагрузки в пиковые периоды**
    - Платформа должна выдерживать кратный (до 5×) рост числа создаваемых тренировок и событий в период глобальных челленджей/кампаний без деградации времени отклика критичных API более чем на 50% от номинала.
3. **Масштабируемость social‑функций**
    - Архитектура ленты активности и лидербордов должна позволять масштабироваться минимум до десятков миллионов событий в сутки без полного пересчёта «с нуля» (через инкрементальные обновления и агрегаты).


### 9.2. Доступность и надёжность

1. **Доступность критичных функций**
    - Доступность основных пользовательских сценариев (создание тренировок, просмотр истории, участие в челленджах) должна составлять не менее 99.5% в месяц для приоритетных регионов.
2. **Сохранность данных тренировок**
    - Любая зафиксированная пользователем тренировка (при наличии соединения либо после успешной синхронизации из офлайн‑буфера) не должна теряться при отказах отдельных сервисов или узлов.
    - В случае частичного сбоя возможна временная задержка отображения в ленте или челлендже, но не потеря записи.
3. **Защита от одиночной точки отказа**
    - Не должно быть single point of failure в слоях: API Gateway, Event Bus, Operational DB для критичных доменов; для каждого должно быть предусмотрено кластерное или управляемое отказоустойчивое решение.
4. **Офлайн‑режим и восстановление**
    - Мобильное приложение должно уметь локально буферизовать данные тренировок и синхронизировать их при восстановлении сети, разрешая конфликты по принципу «последний апдейт» или явных правил с сервера.


### 9.3. Безопасность и конфиденциальность

1. **Аутентификация и авторизация**
    - Все обращения к backend должны быть аутентифицированы (кроме минимального набора публичных ресурсов), доступ — управляться через токены (OAuth2/OIDC).
    - Доступ к административным и B2B‑функциям должен быть защищён ролевой моделью и, при необходимости, MFA.
2. **Шифрование данных**
    - Все сетевые соединения между клиентами, backend‑сервисами и внешними системами должны использовать защищённые протоколы (HTTPS/TLS).
    - Персональные, health‑ и геоданные должны храниться в зашифрованном виде средствами СУБД или облачной платформы.
3. **Приватность и контроль пользователя**
    - Пользователь должен иметь возможность:
        - управлять видимостью профиля и тренировок;
        - включать/отключать публикацию маршрутов;
        - отказываться от участия в глобальных рейтингах;
        - запросить выгрузку и удаление своих данных (в рамках правовой модели).
4. **Минимизация и ограничение доступа**
    - Каждый сервис должен иметь доступ только к тем данным, которые необходимы для его домена (principle of least privilege).
    - Должны быть включены журналы доступа к чувствительным данным с возможностью ретроспективного анализа.


### 9.4. Производительность

1. **Время отклика клиентских сценариев**
    - Загрузка главного экрана и ленты активности — не более 2 секунд при нормальной сети для 95‑го перцентиля.
    - Запрос истории тренировок за последний месяц — не более 2–3 секунд для 95‑го перцентиля.
    - Отображение экрана результата после завершения тренировки — не более 1 секунды после ответа сервера.
2. **Производительность расчётов агрегатов и лидербордов**
    - Обновление агрегатов по тренировке (ежедневные/еженедельные показатели) должно выполняться асинхронно, но так, чтобы пользователь видел обновлённые данные не позднее N секунд после завершения тренировки (значение N задаётся целевыми SLA, например 30–60 секунд).
    - Обновление позиций в лидерборде для челленджа не должно блокировать запись тренировок и должно выполняться инкрементально.
3. **Поддержка конкуррентных пользователей**
    - Система должна поддерживать заданное целевое количество одновременно активных пользователей (например, десятки/сотни тысяч) без существенного роста ошибок и латентности критичных API.


### 9.5. Наблюдаемость

1. **Логирование**
    - Все сервисы должны вести структурированные логи с уровнем, достаточным для диагностики инцидентов (корреляционные ID, ключевые бизнес‑события).
    - Должна быть возможность фильтрации логов по пользователю, запросу, trace‑ID.
2. **Метрики**
    - Для ключевых сервисов должны быть доступны метрики: количество запросов, латентность (p95/p99), процент ошибок, нагрузка на ресурсы, ключевые бизнес‑счётчики (созданные тренировки, участие в челленджах, отправленные уведомления).
3. **Трассировка запросов**
    - Для межсервисных взаимодействий должна быть поддержана распределённая трассировка, позволяющая увидеть цепочку вызовов от мобильного клиента до backend‑сервисов и внешних систем.
4. **Мониторинг и алёртинг**
    - Должны быть настроены дашборды и оповещения по SLA: доступность, время отклика, ошибка интеграций, задержка обработки событий, очереди в шине сообщений.



### 9.6. Расширяемость и модифицируемость

1. **Изоляция доменов**
    - Изменения в логике одного домена (например, новые типы челленджей) не должны требовать модификации других доменов, кроме согласованных контрактов (events, API).
2. **Версионирование контрактов**
    - Публичные API и события должны иметь версионирование, позволяющее вводить новые поля/форматы без одновременного принудительного обновления всех потребителей.
3. **Возможность добавления интеграций**
    - Слой интеграций (devices, B2B) должен поддерживать добавление новых провайдеров без изменения внутренних доменных моделей (через адаптеры/коннекторы).



### 9.7. Юзабилити и UX

1. **Онбординг и время до первой ценности**
    - Пользователь должен иметь возможность:
        - зарегистрироваться;
        - задать базовую цель;
        - записать первую тренировку
за время не более 3–5 минут.
2. **Простота ключевых сценариев**
    - Запуск и завершение тренировки — не более 2–3 экранов/действий.
    - Присоединение к челленджу — не более 3 шагов (найти → прочитать правила → присоединиться).
3. **Консистентность интерфейсов**
    - Во всех основных разделах приложения (тренировки, планы, community, каталог) должны использоваться согласованные паттерны навигации и визуальные элементы.



### 9.8. Эксплуатация и сопровождение

1. **Доступность для DevOps/SRE**
    - Должна быть возможность деплоя и отката отдельных сервисов без простоя всей системы.
    - Инфраструктура должна поддерживать автоматизированный CI/CD с проверками качества (tests, linters, security‑сканы).
2. **Управление конфигурациями**
    - Конфигурации (фичефлаги, лимиты, URL внешних систем, параметры кампаний) не должны требовать пересборки и повторного деплоя сервисов.
3. **Документированность**
    - Архитектура, API и основные бизнес‑процессы должны быть описаны и доступны для команд разработки, эксплуатации и безопасности.
