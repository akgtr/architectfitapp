## 7. Выделение критических бизнес‑сценариев

Ниже — набор сценариев уровня «user journey», которые напрямую поддерживают наши бизнес‑цели (community‑first, персонализация, commerce, платформа) и будут драйвить архитектурные решения.


### 7.1. Ежедневная тренировка и сравнение с собой

**Цель:** пользователь быстро фиксирует тренировку, видит свой прогресс и получает базовую мотивацию.

**Сценарий:**

1. Пользователь открывает приложение и запускает тренировку (или импортирует её из системы телефона / устройства).
2. Во время и после тренировки собираются ключевые метрики (дистанция, время, пульс и т.д.).
3. По завершении пользователь видит экран результата с сравнением: «сегодня» vs «предыдущие тренировки» и личные рекорды.
4. Тренировка попадает в историю, агрегаты обновляются (за неделю/месяц), данные доступны для планов, челленджей и commerce.

**Почему критично:**

- Это базовый сценарий, без него приложение теряет смысл как фитнес‑инструмент.
- От качества и надёжности здесь зависят все остальные фичи (персонализация, челленджи, рекомендации, inventory).

**Диаграмма последовательности**

```mermaid
sequenceDiagram
    actor User as Пользователь
    participant App as Мобильное приложение
    participant Auth as Сервис авторизации
    participant Backend as Backend платформа
    participant DB as База данных (History & Stats)

    User->>App: Открывает приложение
    App->>Auth: Проверка токена сессии
    Auth-->>App: Сессия активна (Профиль пользователя)
    App->>User: Главный экран (План на сегодня)

    User->>App: Запускает тренировку (Start)
    
    Note over App: Активация GPS / Датчиков пульса
    App->>App: Локальная запись данных (Офлайн-режим)

    loop В процессе тренировки
        User->>App: Выполняет активность
        App->>User: Real-time метрики (Темп, Пульс, Время)
    end

    User->>App: Завершает тренировку (Stop)
    
    rect rgb(240, 248, 255)
    Note right of App: Синхронизация данных
    App->>Backend: POST /training/upload (Raw Data)
    
    Backend->>Backend: Валидация данных (Анти-чит)
    Backend->>DB: Сохранение тренировки
    Backend->>DB: Пересчёт агрегатов (Неделя/Месяц)
    Backend->>DB: Проверка личных рекордов (PB)
    
    Backend-->>App: JSON: Сводка, Сравнение, Рекорды
    end

    App->>User: Экран результата: "Сегодня" vs "Среднее"
    App->>User: Анимация рекорда + Графики прогресса
    
    Note over User, App: Данные доступны для Челленджей (7.2)
```

### 7.2. Присоединение к челленджу и участие в нём

**Цель:** усилить мотивацию через соревнование (прежде всего с собой и ближайшим кругом), поддержать community‑first.

**Сценарий:**

1. Пользователь видит в приложении доступные челленджи (личные, групповые, региональные, корпоративные).
2. Выбирает челлендж (например, «пробежать 30 км за 7 дней»), читает правила, присоединяется.
3. В течение периода его тренировки автоматически учитываются в прогрессе челленджа.
4. Пользователь периодически открывает экран челленджа и видит: свой прогресс, позицию в таблице лидеров, прогресс друзей/группы.
5. По завершении челленджа он получает результат, уведомление, бейдж/награду и, возможно, персональное предложение от бренда.

**Почему критично:**

- Это основной сценарий, где сходятся community, тренировки, персонализация и commerce.
- От корректности расчётов и отзывчивости зависят доверие к системе и мотивация продолжать.

**Диаграмма последовательности**

```mermaid
sequenceDiagram
    actor User as Пользователь
    participant App as Мобильное приложение
    participant Backend as Backend платформа
    participant DB as База данных / Кэш

    User->>App: Открывает раздел "Челленджи"
    App->>Backend: Запрос доступных челленджей (личные, группы, бренды)
    Backend->>DB: Получение списка активных событий
    DB-->>Backend: Список челленджей
    Backend-->>App: Список с фильтрацией по профилю
    App->>User: Отображает витрину челленджей

    User->>App: Выбирает челлендж и нажимает "Присоединиться"
    App->>Backend: Регистрация участия (UserID, ChallengeID)
    Backend->>DB: Создание записи участия, проверка условий
    DB-->>Backend: Ок
    Backend-->>App: Подтверждение участия + правила/цели

    Note over User, Backend: Период проведения челленджа

    loop Каждая новая тренировка
        App->>Backend: Отправка данных тренировки (см. сценарий 7.1)
        Backend->>Backend: Проверка соответствия условиям челленджа
        alt Тренировка подходит под условия
            Backend->>DB: Обновление прогресса в челлендже
            Backend->>Backend: Пересчёт позиции в таблице лидеров
        end
    end

    User->>App: Открывает экран челленджа
    App->>Backend: Запрос текущего статуса и Leaderboard
    Backend-->>App: Прогресс, позиция, статус друзей
    App->>User: Показывает прогресс-бар и место в рейтинге

    Note over User, Backend: Завершение челленджа

    Backend->>Backend: Фиксация финальных результатов
    Backend->>DB: Выдача наград (бейджи, баллы)
    Backend-->>App: Push-уведомление о завершении и результате
    
    App->>User: Показ экрана итогов: награда + персональное предложение
```


### 7.3. Создание и поддержание привычки через персональный план

**Цель:** перевести пользователя от разовых тренировок к регулярному, структурированному процессу.

**Сценарий:**

1. На онбординге или позже пользователь выбирает цель (например, «подготовиться к 5 км за 8 недель»).
2. Система предлагает план на основе уровня, истории и доступного времени.
3. Пользователь подтверждает план, видит календарь тренировок и ближайшую сессию.
4. В течение недели он получает уведомления о запланированных тренировках, может переносить/облегчать их.
5. При пропусках или перевыполнении план автоматически адаптируется (добавляет лёгкие сессии, снижает нагрузку и т.п.).
6. Пользователь видит прогресс по плану (процент выполнения, оставшиеся недели, улучшение ключевых метрик).

**Почему критично:**

- План — главный инструмент формирования долгосрочной привычки и удержания.
- На его основе строятся персональные рекомендации, мотивационные уведомления и часть промо (экипировка под план).

**Диаграмма последовательности**

```mermaid
sequenceDiagram
    actor User as Пользователь
    participant App as Мобильное приложение
    participant ML as ML-движок / Рекомендатор
    participant Backend as Backend платформа
    participant DB as База данных (Планы и Календарь)

    Note over User, App: Этап 1: Формирование плана
    User->>App: Выбирает цель (напр. "5 км за 8 недель")
    App->>Backend: Запрос на генерацию плана (Цель + Профиль + История)
    Backend->>ML: Анализ данных пользователя и расчет нагрузки
    ML-->>Backend: Оптимальный график тренировок
    Backend-->>App: Предварительный план и календарь
    
    User->>App: Подтверждает план
    App->>Backend: Активация плана
    Backend->>DB: Сохранение расписания и установка триггеров уведомлений
    Backend-->>App: План активирован. Ближайшая тренировка: Завтра

    Note over User, App: Этап 2: Поддержание привычки (Цикл)

    loop Каждую неделю / день
        Backend->>App: Push-уведомление: "Сегодня по плану интервальный бег"
        User->>App: Выполняет тренировку (см. сценарий 7.1)
        App->>Backend: Отправка результатов тренировки
        
        alt Тренировка выполнена успешно
            Backend->>DB: Обновление прогресса плана (%)
            Backend-->>App: "Отлично! Вы выполнили 40% плана"
        else Пропуск или перевыполнение нагрузки
            Backend->>ML: Запрос на адаптацию плана
            ML-->>Backend: Скорректированный график (облегчение/усложнение)
            Backend->>DB: Обновление расписания в календаре
            Backend-->>App: "План адаптирован под ваш темп"
        end
    end

    Note over User, App: Этап 3: Анализ прогресса
    User->>App: Открывает экран прогресса плана
    App->>Backend: Запрос аналитики по плану
    Backend->>DB: Сбор метрик (выполнение, рост выносливости)
    Backend-->>App: Данные для графиков и прогноз завершения
    App->>User: Визуализация: % выполнения, прогноз и рекомендации по экипировке
```


### 7.4. Социальное взаимодействие: поддержка и групповые активности

**Цель:** создать ощущение комьюнити и социальной поддержки, без превращения в тяжёлую соцсеть.

**Сценарий:**

1. Пользователь находит знакомых или коллег (по контактам, QR, поиску), добавляет их в друзья.
2. Вступает в локальный клуб/группу по интересам (например, «Минск, вечерние пробежки»).
3. После тренировки его результат появляется в ленте друзей/группы.
4. Друзья оставляют реакции и короткие комментарии, приглашают в совместный челлендж или на офлайн‑тренировку.
5. Группа создаёт свой челлендж/ивент, участники присоединяются, видят общий прогресс и общие результаты.

**Почему критично:**

- Социальная поддержка и чувство принадлежности — ключевые факторы долгосрочного удержания в фитнес‑приложениях.
- Сценарий влияет на требования к ленте, группам, приватности и модерации.

**Диаграмма последовательности**

```mermaid
sequenceDiagram
    actor User as Пользователь
    actor Friend as Друг / Участник группы
    participant App as Мобильное приложение
    participant Backend as Backend платформа
    participant Social as Социальный модуль (Лента, Группы)
    participant DB as База данных (Связи и Контент)

    Note over User, App: Этап 1: Построение социального графа
    User->>App: Открывает раздел "Друзья"
    App->>Backend: Запрос рекомендаций (Контакты, QR, Поиск)
    Backend->>DB: Поиск по телефону / никнейму
    DB-->>Backend: Список потенциальных друзей
    Backend-->>App: Рекомендации + Взаимные друзья
    
    User->>App: Отправляет запрос в друзья
    App->>Backend: POST /friends/request
    Backend->>DB: Создание связи (Pending)
    Backend-->>Friend: Push-уведомление: "User хочет добавить вас"
    Friend->>App: Принимает запрос
    App->>Backend: Подтверждение связи
    Backend->>DB: Обновление статуса (Friends)

    Note over User, App: Этап 2: Вступление в группу
    User->>App: Ищет группу "Минск, вечерние пробежки"
    App->>Backend: Запрос локальных групп (Геолокация + Интересы)
    Backend->>Social: Фильтрация активных групп
    Social-->>Backend: Список групп с метаданными
    Backend-->>App: Карточки групп (Участники, Активность)
    
    User->>App: Вступает в группу
    App->>Backend: POST /groups/join
    Backend->>DB: Добавление в список участников
    Backend-->>App: "Вы теперь участник группы"

    Note over User, Friend: Этап 3: Публикация активности и взаимодействие
    User->>App: Завершает тренировку (см. сценарий 7.1)
    App->>Backend: Публикация результата в ленту
    Backend->>Social: Формирование поста (Метрики + Карта маршрута)
    Social->>DB: Сохранение поста с настройками приватности
    
    Backend-->>Friend: Обновление ленты друзей/группы
    Friend->>App: Видит пост в ленте
    Friend->>App: Оставляет реакцию 👍 или комментарий
    App->>Backend: POST /activity/react
    Backend->>DB: Сохранение реакции
    Backend-->>User: Push: "Friend отреагировал на вашу тренировку"

    Note over User, Friend: Этап 4: Создание группового челленджа
    User->>App: Создает челлендж для группы "100 км за месяц"
    App->>Backend: POST /challenges/create (Group-scoped)
    Backend->>Social: Валидация прав (Админ группы?)
    Social->>DB: Создание челленджа с привязкой к группе
    Backend-->>Friend: Push всем участникам группы: "Новый челлендж!"
    
    Friend->>App: Присоединяется к челленджу (см. сценарий 7.2)
    
    loop В течение челленджа
        User->>App: Выполняет тренировки
        Backend->>Social: Обновление общего прогресса группы
        Social-->>App: Отображение в ленте: "Группа прошла 45/100 км"
    end

    Backend->>Social: Завершение челленджа, подсчет результатов
    Social-->>User: "Ваша группа завершила челлендж! 🎉"
    Social-->>Friend: Общая статистика и топ участников
```

### 7.5. Использование и обновление инвентаря (связка с коммерцией)

**Цель:** нативно связать реальные тренировки и инвентарь пользователя с рекомендациями и продажами.

**Сценарий:**

1. Пользователь добавляет свои кроссовки/инвентарь (выбор модели из бренда или ввод вручную).
2. Во время тренировок пробег/использование автоматически накапливается.
3. При достижении порога (например, 600–800 км) пользователь получает уведомление: «кроссовкам пора на замену» + подборку моделей бренда.
4. На экране инвентаря пользователь видит статус: «новые», «в активном использовании», «рекомендуется замена».
5. По клику на рекомендацию он попадает на карточку товара в основном e‑commerce (deeplink).

**Почему критично:**

- Это ключевой «мост» между тренировками и бизнес‑результатами (LTV, продажи).
- Требует корректной интеграции данных тренировок, каталога и промо, а также аккуратного UX (чтобы не выглядеть навязчивой рекламой).

**Диаграмма последовательности**

```mermaid
sequenceDiagram
    actor User as Пользователь
    participant App as Мобильное приложение
    participant Backend as Backend платформа
    participant Inventory as Сервис инвентаря
    participant Commerce as E-commerce система (Каталог + Корзина)
    participant DB as База данных (Gear & Usage)

    Note over User, App: Этап 1: Добавление инвентаря
    User->>App: Открывает раздел "Мой инвентарь"
    App->>User: Показывает список текущего инвентаря
    
    User->>App: Добавляет новые кроссовки
    App->>Backend: Запрос каталога брендов и моделей
    Backend->>Commerce: GET /catalog/shoes (Бренды-партнеры)
    Commerce-->>Backend: Список моделей с метаданными
    Backend-->>App: Карточки кроссовок для выбора
    
    User->>App: Выбирает модель или вводит вручную
    App->>Backend: POST /inventory/add (Model, Start Date, Initial Mileage)
    Backend->>Inventory: Создание записи инвентаря
    Inventory->>DB: Сохранение с установкой счетчика (0 км)
    Backend-->>App: "Кроссовки добавлены. Статус: Новые"

    Note over User, App: Этап 2: Автоматический учет использования
    loop Каждая тренировка (см. сценарий 7.1)
        User->>App: Завершает тренировку с дистанцией
        App->>Backend: POST /training/upload (Distance, Gear ID)
        Backend->>Inventory: Обновление пробега инвентаря
        Inventory->>DB: Increment mileage (+10 км)
        
        alt Пробег достиг порога (600-800 км)
            Inventory->>Backend: Триггер: "Gear needs replacement"
            Backend->>Commerce: Запрос персональных рекомендаций (User Profile + Gear Model)
            Commerce-->>Backend: Подборка новых моделей + Промо
            Backend-->>App: Push-уведомление: "Пора обновить кроссовки! 🎯"
        end
    end

    Note over User, App: Этап 3: Просмотр статуса и переход к покупке
    User->>App: Открывает экран инвентаря
    App->>Backend: GET /inventory/status
    Backend->>Inventory: Получение актуального состояния
    Inventory-->>Backend: Список с метриками (Пробег, Статус, Рекомендации)
    Backend-->>App: Визуализация: "В использовании: 650 км / Рекомендуется замена"
    
    User->>App: Нажимает на рекомендацию "Посмотреть новые модели"
    App->>Backend: GET /commerce/recommendations (Gear ID)
    Backend->>Commerce: Запрос персонализированной подборки
    Commerce-->>Backend: Deeplink + Карточки товаров с ценами
    Backend-->>App: Открытие встроенного WebView или переход в E-commerce
    
    User->>Commerce: Просматривает товар, добавляет в корзину
    Commerce->>Commerce: Оформление заказа (вне scope фитнес-приложения)
    Commerce-->>Backend: Webhook: "Order placed" (для аналитики)
    Backend->>DB: Логирование конверсии (Attribution)
    
    Note over User, Backend: Опционально: Обновление инвентаря после покупки
    Backend-->>App: Предложение: "Добавить новые кроссовки в инвентарь?"
    User->>App: Подтверждает
    App->>Backend: POST /inventory/add (New Model, Auto-retire Old)
    Backend->>Inventory: Архивация старых, активация новых
    Inventory->>DB: Обновление статусов
```

### 7.6. Корпоративный / массовый сценарий: командный челлендж

**Цель:** поддержать B2B‑использование и массовые мероприятия, важные для бренда.

**Сценарий:**

1. Представитель компании или организатор события создаёт корпоративный/массовый челлендж (например, «команды департаментов, кто больше пройдет шагов за месяц»).
2. Сотрудники/участники получают приглашения, присоединяются через приложение.
3. В течение периода система агрегирует данные по участникам и командам (шаги, активные минуты и т.п.).
4. Организатор и участники видят рейтинг команд, общий прогресс и финальные результаты.
5. Бренд может связать награды/призы с продукцией и промо‑кампаниями.

**Почему критично:**

- Даёт дополнительный канал монетизации и продвижения через B2B и события.
- Накладывает требования к масштабируемости, отчётности и ролям/доступам.

**Диаграмма последовательности**

```mermaid
sequenceDiagram
    actor Org as Организатор / Компания
    actor User as Участник
    participant App as Мобильное приложение
    participant Backend as Backend платформа
    participant Corp as Корпоративный модуль (Админка B2B)
    participant Social as Социальный/Челлендж модуль
    participant Analytics as Сервис агрегирования и расчётов
    participant DB as База данных (Команды, Челленджи, Метрики)
    participant Commerce as E-commerce / Промо-система

    Note over Org, Corp: Этап 1: Создание корпоративного челленджа
    Org->>Corp: Создаёт челлендж (Период, Тип метрики, Призы)
    Corp->>Backend: POST /corp/challenges/create
    Backend->>DB: Создание записи челленджа
    Backend->>Social: Инициализация сущности челленджа
    Social-->>Backend: Челлендж готов
    
    Org->>Corp: Загружает команды (CSV / вручную)
    Corp->>Backend: POST /corp/challenges/teams
    Backend->>DB: Создание команд + участников (pending)
    Backend-->>Org: Всё готово, можно приглашать сотрудников

    Note over User, App: Этап 2: Присоединение участников
    Backend-->>User: Push/email приглашение: "Присоединяйтесь к корпоративному челленджу"
    User->>App: Открывает приглашение
    App->>Backend: GET /corp/invite/validate
    Backend->>DB: Проверка принадлежности к команде
    Backend-->>App: Приглашение валидно
    
    User->>App: Присоединяется
    App->>Backend: POST /corp/challenges/join (User ID)
    Backend->>DB: Статус участника -> Active
    Backend-->>User: "Вы присоединились к команде X"

    Note over User, Analytics: Этап 3: Агрегация активности (в течение всего периода)
    loop Каждый день / час
        User->>App: Выполняет тренировку или собирает шаги
        App->>Backend: POST /metrics/upload (steps, active_minutes, etc.)
        Backend->>DB: Сохранение сырых данных
 
        Backend->>Analytics: Триггер перерасчёта командных агрегатов
        Analytics->>DB: Агрегация (Сумма шагов команды, Top performer, Ср. активность)
        Analytics-->>Backend: Обновлённые метрики челленджа
    end

    Note over User, Org: Этап 4: Просмотр рейтингов и прогресса
    User->>App: Открывает экран челленджа
    App->>Backend: GET /corp/challenges/leaderboard
    Backend->>Analytics: Запрос актуального рейтинга
    Analytics->>DB: Чтение агрегатов
    Analytics-->>Backend: Рейтинг команд + личные метрики
    Backend-->>App: Отображение: "Команда A лидирует", "Ваш вклад: 13 500 шагов"

    Org->>Corp: Открывает админ‑панель
    Corp->>Backend: GET /corp/challenges/stats
    Backend->>Analytics: Запрос отчётности (в разрезах: команда, отдел, участник)
    Analytics-->>Backend: Полные таблицы метрик
    Backend-->>Org: Дашборд для организатора

    Note over Org, Commerce: Этап 5: Призы, награды и связь с промо
    Org->>Corp: Настраивает призы или купоны (победителям / всем)
    Corp->>Commerce: Создание промокодов или товарных наград
    Commerce-->>Backend: Подтверждение + deeplinks
    Backend-->>User: Push: "Ваша команда победила! Получите награду 🎉"
    
    User->>App: Переходит по deeplink в Commerce
    Commerce->>Commerce: Оформление заказа / активация купона
    
    Note over Backend: Фиксация атрибуции
    Commerce-->>Backend: Webhook: "Prize claimed"
    Backend->>DB: Запись взаимодействия (Analytics, ROI)
```

### 7.7. Сценарий приватности и контроля над данными

**Цель:** дать пользователю чувство контроля над тем, что и кому видно, и тем самым снизить барьер использования.

**Сценарий:**

1. При онбординге пользователь видит экран согласий (персональные данные, health‑данные, геолокация) и может гибко настроить разрешения.
2. В настройках есть раздел «Приватность»:
    - видимость профиля (все, только друзья, никто);
    - видимость тренировок и маршрутов (полная карта, только суммарные показатели, скрыть полностью);
    - участие в глобальных рейтингах и публичных челленджах.
3. Пользователь в любой момент может изменить настройки и запросить выгрузку/удаление своих данных.

**Почему критично:**

- Без доверия к приватности пользователи не будут делиться реальными данными (особенно гео и health), а значит потеряется ценность community и персонализации.
- Влияет на архитектурные решения по данным, IAM, event‑модели и отображению информации.

**Диаграмма последовательности**

```mermaid
sequenceDiagram
    actor User as Пользователь
    participant App as Мобильное приложение
    participant Auth as IAM / Авторизация
    participant Backend as Backend платформа
    participant Privacy as Приватность / Consent Service
    participant Social as Социальные сервисы (Лента, Профиль, Группы)
    participant Activity as Тренировки и Метрики
    participant Compliance as Compliance / DSR (удаление, выгрузка)
    participant DB as База данных (Профиль, Настройки, Согласия)

    Note over User, App: Этап 1: Онбординг и сбор согласий
    User->>App: Старт онбординга
    App->>User: Экран согласий (данные здоровья, геолокация, social)
    
    User->>App: Выбирает разрешения
    App->>Backend: POST /privacy/consent (Geo = Off, Health = On, etc.)
    Backend->>Privacy: Сохранение consent-политики
    Privacy->>DB: Запись настроек согласий
    Backend-->>App: Онбординг завершён

    Note over User, App: Этап 2: Настройки приватности
    User->>App: Переходит в «Приватность»
    App->>Backend: GET /privacy/settings
    Backend->>Privacy: Получение текущей политики
    Privacy-->>Backend: Параметры видимости
    Backend-->>App: Отображение настроек

    User->>App: Меняет настройки (Профиль → Только друзья)
    App->>Backend: POST /privacy/update
    Backend->>Privacy: Обновление правил доступа
    Privacy->>DB: Перезапись политики уровня пользователя

    Note over User, Backend: Этап 3: Применение приватности при использовании системы

    User->>Activity: Выполняет тренировку (см. 7.1)
    Activity->>Backend: Передаёт результат
    
    alt Видимость тренировок = "Только суммарные данные"
        Backend->>Privacy: Проверка режима публикации
        Privacy-->>Backend: Hide route, keep summary
        Backend->>Social: Публикация без GPS‑маршрута
    else Видимость = "Никто"
        Backend->>Social: Не публикуем в ленту
    else Полная видимость
        Backend->>Social: Публикация с картой маршрута
    end

    Note over Social: Лента других пользователей фильтруется по приватности
    Social->>Privacy: Проверка доступа (Friend? Public?)
    Privacy-->>Social: Allow / Deny
    Social-->>User: Отображение в ленте (или скрыто)

    Note over User, App: Этап 4: Участие в глобальных рейтингах
    User->>App: Выключает участие в глобальных рейтингах
    App->>Backend: POST /privacy/leaderboards=off
    Backend->>Privacy: Обновление флага LeaderboardOptOut
    Privacy->>DB: Сохранение настроек
    
    Backend->>Activity: Исключить данные из глобальных агрегатов
    Backend-->>User: Настройки обновлены

    Note over User, Compliance: Этап 5: Выгрузка или удаление данных (DSR)
    User->>App: Запрашивает выгрузку данных ("Download my data")
    App->>Backend: POST /privacy/export-request
    Backend->>Compliance: Запуск процесса
    Compliance->>DB: Сбор профиля, активностей, согласий
    Compliance-->>Backend: ZIP archive / JSON bundle готов
    Backend-->>App: Ссылка на скачивание

    User->>App: Запрашивает удаление данных ("Right to be forgotten")
    App->>Backend: POST /privacy/delete-request
    Backend->>Compliance: Инициировать удаление
    Compliance->>DB: Деактивация профиля, удаление персональных данных
    Compliance->>Social: Анонимизация постов/реакций
    Compliance->>Activity: Удаление health/geo‑данных
    Compliance-->>Backend: Процесс завершён
    Backend-->>User: Уведомление: Данные удалены
```

### 7.8. Сценарий восстановления после проблем связи (офлайн → онлайн)

**Цель:** обеспечить надёжность ключевых сценариев тренировки и участия в челленджах в условиях плохой связи.

**Сценарий:**

1. Пользователь запускает тренировку в месте с плохим интернетом (лес, горы, «дикие» локации).
2. Тренировка записывается локально, данные о маршруте и метриках буферизуются в приложении.
3. При восстановлении соединения приложение синхронизирует тренировку с сервером, обновляет историю, прогресс челленджей и ленту.
4. Пользователь видит свои результаты и обновлённые рейтинги, как будто тренировка была онлайн.

**Почему критично:**

- Реальные спортивные активности часто происходят не в идеальных сетевых условиях.
- Потеря тренировки — один из самых болезненных сценариев для пользователя и бренда.

**Диаграмма последовательности**

```mermaid
sequenceDiagram
    actor User as Пользователь
    participant App as Мобильное приложение
    participant Storage as Локальный буфер / SQLite
    participant Backend as Backend платформа
    participant Activity as Сервис тренировок
    participant Challenges as Челленджи / Лидеры
    participant Social as Лента / Feed
    participant Inventory as Инвентарь (Mileage)
    participant DB as База данных

    Note over User, App: Этап 1: Запуск тренировки в плохой сети
    User->>App: Запускает тренировку
    App->>User: Показ метрик в реальном времени
    App-->>Backend: Попытка соединения (нет сети)
    App->>Storage: Создание локальной сессии (SessionID, StartTime)

    Note over App, Storage: Этап 2: Запись данных в офлайне
    loop В процессе тренировки
        App->>Storage: Сохранение GPS-точек, пульса, темпа (batch)
        App->>User: Локальная визуализация характера тренировки
    end

    User->>App: Завершает тренировку
    App->>Storage: Финализация локальной записи (Raw Data + Meta)

    Note over App, Backend: Этап 3: Автосинхронизация после появления сети
    App-->>Backend: Ping /status (сеть восстановилась)
    
    App->>Backend: POST /training/upload (SessionID + Raw Data)
    Backend->>Activity: Идемпотентная обработка (If SessionID exists → skip)
    Activity->>DB: Сохранение тренировки + агрегация
    Activity-->>Backend: Тренировка обработана

    Note over Backend: Триггеры после успешного аплоада
    Backend->>Challenges: Обновление прогресса челленджа (km, steps)
    Challenges->>DB: Пересчёт рейтингов и статусов
    Backend->>Inventory: Обновление пробега экипировки
    Inventory->>DB: Increment mileage
    
    Backend->>Social: Публикация тренировки (учёт приватности)
    Social->>DB: Создание поста (с картой/без — зависит от настроек)
    
    Backend-->>App: Возврат агрегатов: Прогресс челленджа, общее расстояние, новые рейтинги

    Note over App, User: Этап 4: Отрисовка результатов после синхронизации
    App->>User: Финальный экран: Дистанция, маршруты, рекорды
    App->>User: Обновлённые челленджи, позиции в рейтинге и лента
    App->>Storage: Помечает локальную запись как синхронизированную

    Note over User, App: Поведение в случае конфликтов (редко)
    alt Серверная версия и локальная отличаются
        Backend-->>App: Команда перепривязки или мерджа данных
        App->>User: Запрос подтверждения (только в сложных кейсах)
    else Идемпотентный аплоад → нет конфликтов
        Backend-->>App: Успешная синхронизация
    end
```
